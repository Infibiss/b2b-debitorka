# Эксплуатация AgentPay

Дата: 24.10.2026. Текущая схема: один контейнер, один uvicorn worker, SQLite WAL на постоянном диске. Это первый сопровождаемый пилот; HA, несколько реплик, многопользовательские роли, MFA, восстановление пароля, проверка email и автоматический биллинг пока отсутствуют. Перед открытой коммерческой регистрацией определить процесс поддержки и восстановления доступа.

## 1. Конфигурация

| Переменная | Значение/поведение |
|---|---|
| `APP_ENV` | `production` включает требования безопасной конфигурации и выключает API docs |
| `APP_TIMEZONE` | `Europe/Moscow` по умолчанию. IANA-пояс для договорных календарных дат, aging, обещаний и недельного графика; неверное значение блокирует запуск. Технические события/сессии остаются UTC |
| `APP_URL` | Полный внешний origin без пути. Вне Render обязателен в production; в Render можно не задавать/оставить пустым — используется автоматический `RENDER_EXTERNAL_URL`. Для собственного домена задать явно: он имеет приоритет. Использовать ASCII/punycode домен при IDN |
| `RENDER_EXTERNAL_URL` | Автоматический полный HTTPS `onrender.com` URL от Render; запасной адрес при пустом/отсутствующем `APP_URL`. Не требуется создавать эту переменную вручную |
| `SECURE_COOKIES` | `true` в production; `false` только для локального HTTP |
| `DATABASE_PATH` | В контейнере `/var/data/agentpay.db`; каталог должен быть на постоянном диске и доступен UID/GID 10001 |
| `PORT` | Порт контейнера, 10000 по умолчанию. Docker CMD подставляет его в uvicorn |
| `SMTP_HOST`, `SMTP_FROM` | Обязательны для фактической отправки. Без них письма только сохраняются |
| `SMTP_TENANT_ID` | UUID единственной организации, которой разрешен серверный SMTP. Без привязки отправка отключена; чужие tenant использовать ящик не могут |
| `SMTP_PORT` | 587 по умолчанию; использовать выданный провайдером |
| `SMTP_USER`, `SMTP_PASSWORD` | Авторизация, если необходима SMTP-провайдеру |
| `SMTP_USE_TLS` | `true` по умолчанию: STARTTLS для обычного SMTP |
| `SMTP_USE_SSL` | `false` по умолчанию; `true` для implicit TLS, обычно порт 465. Тогда STARTTLS не применяется |
| `YANDEX_API_KEY`, `YANDEX_MODEL` | Необязательная связка для AI Studio. API-ключ и полный `gpt://folder/...` URI модели; без них работают шаблоны |

Окружение передается хостингом/оболочкой: чтения `.env` в коде нет. Не передавать секреты в Vite-prefixed переменные, Docker build args, GitHub artifacts и логи. В этом выпуске один серверный SMTP привязан к одному tenant; отдельного хранилища секретов SMTP для каждого клиента нет. Для первых клиентов нужен согласованный канал отправки и право использовать `SMTP_FROM`.

После регистрации уполномоченной организации получить ее UUID доверенным операторским запросом с параметром email (не помещать SQL из пользовательского ввода напрямую в строку):

```bash
python -c '
import os, sqlite3
from pathlib import Path
email = input("Email зарегистрированного владельца: ").strip().lower()
database = Path(os.environ["DATABASE_PATH"]).resolve()
with sqlite3.connect(database.as_uri() + "?mode=ro", uri=True) as connection:
    row = connection.execute("SELECT tenant_id FROM users WHERE email=?", (email,)).fetchone()
    if row is None:
        raise SystemExit("Пользователь не найден; SMTP не привязан")
    print(row[0])
'
```

Задать результат как `SMTP_TENANT_ID` в окружении хостинга и перезапустить сервис. Проверить, что именно этот аккаунт показывает настроенный SMTP, а другой — отключенный. Не выводить таблицу пользователей целиком.

При включении Yandex интеграция обращается к фиксированному официальному HTTPS endpoint, передавая только общий запрос/тон (`soft`/`firm`). Счета, контакты, название клиента и остаток не передаются. Финансовое предложение вставляет код после проверки трех коротких фраз; цифры, ссылки и ряд финансовых/правовых утверждений запрещены фильтром. Ошибка, тайм-аут или неподходящий ответ ведут к шаблону. Фильтры не являются доказательством полной безопасности свободного текста: пользователь проверяет черновик до согласования. Ключ дает доступ к платному провайдеру — установить квоты/лимиты расходов и согласовать условия обработки. Реальная доставка/ответ Yandex требуют своих доступов и отдельной проверки.

Разрешенный origin (scheme+host+port) определяется через `APP_URL`, либо `RENDER_EXTERNAL_URL` при его отсутствии. Production по-прежнему требует HTTPS и Secure cookie. После смены домена обновить `APP_URL`, проверить cookie и вход/импорт на новом адресе. Открытый альтернативный домен не будет работать для записи до настройки канонического origin. Сервис за reverse proxy должен иметь ограничения размеров/скорости запросов; встроенные лимиты процессные и не заменяют защиту публичного периметра. Доверенные proxy headers настраивать по реальной топологии, не доверять произвольному `X-Forwarded-For` от интернета. Render описывает автоматический URL в [официальном реестре переменных](https://render.com/docs/environment-variables).

## 2. Render: только публичный/синтетический запуск по умолчанию

Blueprint использует сервис `agentpay-b2b`, Docker, `0.5c-512mb` (0.5 CPU, 512 MB), Frankfurt, один экземпляр, диск 1 GB в `/var/data`, health `/api/health`. Идентификатор тарифа подтвержден [официальной спецификацией Blueprint](https://render.com/docs/blueprint-spec). В подключенном аккаунте 24.10.2026 интерфейс показал $7/месяц за compute и $0.25/месяц за выбранный диск 1 GB; окончательный счет и дополнительные расходы проверять перед созданием ресурса. **Это зарубежное размещение; до отдельного решения по российским данным — только сайт и синтетические данные.** Даже регистрационный email реального человека может быть персональными данными; для теста использовать специально созданные тестовые учетные данные.

1. Подключить свой GitHub-репозиторий к Render Blueprint и проверить расходы платного сервиса/диска.
2. Для стандартного `onrender.com` домена оставить `APP_URL` незаданным/пустым: приложение использует `RENDER_EXTERNAL_URL`. Для собственного домена задать полный HTTPS `APP_URL` вручную. Проверить выбранный Auto-Deploy **After CI Checks Pass**.
3. Проверить, что `DATABASE_PATH` находится под реальным смонтированным `/var/data` и процесс UID 10001 может создавать/читать файлы. Ошибку прав исправлять настройками/владельцем тома, не запуском приложения root.
4. Дождаться успешной сборки и `/api/health`, открыть сайт, зарегистрировать синтетический аккаунт, создать искусственный счет, перезапустить сервис и проверить сохранность.
5. Настроить свою копию БД и проверку восстановления. Диск сам по себе не является резервной копией.

Без диска Render использует временную файловую систему. Данные вне mountPath теряются при deploy/restart. Диск доступен только одному экземпляру и только во время работы сервиса: ни build/pre-deploy, ни отдельная cron job не получают к нему доступ. Deploy с диском имеет перерыв; не обещать zero downtime. Это ограничения Render из [официальной документации дисков](https://render.com/docs/disks).

База создается/мигрируется автоматически при запуске приложения, текущий `PRAGMA user_version=1`. Более новая неизвестная версия схемы блокирует запуск. Перед сменой кода с миграцией делать проверенную копию; откат образа не гарантирует совместимость с новой схемой.

## 3. CI/CD

GitHub Actions проверяет Python API/ops, аудит runtime-зависимостей через `pip-audit`, npm audit с порогом high, TypeScript, production build, Chromium e2e и Docker build. Аудит запускается после установки соответствующих зависимостей; ошибка реестра не обходится как успешная проверка. Основной CD выполняет Render нативно: `autoDeployTrigger: checksPass` соответствует **After CI Checks Pass**. Подключенная ветка публикуется только после успешных CI-проверок нового commit. По [документации Render](https://render.com/docs/deploys#configuring-auto-deploys), заключения GitHub `success`, `neutral` и `skipped` разрешают deploy; отсутствие проверок или любая ошибка его блокируют.

Альтернативный legacy hook-job по умолчанию пропущен. Для его использования сначала установить **Off** в Render и `autoDeployTrigger: "off"` в Blueprint, затем задать GitHub repository variable `RENDER_DEPLOY_MODE=hook` и secret `RENDER_DEPLOY_HOOK`. Одновременно нативный CD и hook не включать — иначе возможны два deploy одного изменения. Hook-job зависит от успешной проверки, работает только на `push` в `main` и передает `ref=GITHUB_SHA`. `pull_request` и ручной `workflow_dispatch` hook не вызывают. [Render документирует ref конкретного SHA](https://render.com/docs/deploy-hooks).

После нативного или hook-trigger проверить статус Render и health, вход и сохранность данных. Ответ 200/202 альтернативного hook означает начало/постановку deploy, не завершение. При отказе hook job завершается ошибкой и не печатает URL/тело ответа. Для первого создания владелец подтверждает платный compute/диск; подключенные аккаунты и успешный CI сами по себе не означают завершенный deploy.

## 4. Размещение для реальных российских клиентов

Использовать тот же контейнер на выбранной и проверенной инфраструктуре в РФ: TLS reverse proxy, один экземпляр, постоянный локальный том, копии и содержащие данные журналы в согласованном месте. Явно проверить владельца/физическое размещение инфраструктуры, субподрядчиков и направления передачи, включая поддержку, почту и внешнюю аналитику. Расположение только основной БД не решает весь вопрос обработки данных.

До импорта контактов/переписки владелец утверждает действующую юридическую схему, основания, поручение обработки, политику и сроки хранения/удаления. Текст этих документов зависит от реальных реквизитов и не придуман в репозитории. В исследовании [ML и данных](research/ml-data.md) отмечены пределы проверки редакции 152-ФЗ на дату работы. Здесь не заявляется автоматическое соответствие 152-ФЗ.

Масштабировать этот вариант количеством uvicorn workers/реплик не следует: серверные лимиты находятся в памяти процесса, SQLite использует один файл. При необходимости нескольких реплик сначала спроектировать PostgreSQL, общие сессии/лимиты, очередь отправки и миграцию. Этот переход пока не реализован.

## 5. Резервная копия

Используется [SQLite backup API](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.Connection.backup), который получает согласованную копию, включая зафиксированные данные WAL. Нельзя копировать только `.db` работающего WAL-приложения обычным `cp`. Скрипт отказывается перезаписывать существующий файл, проверяет `integrity_check` и создает копию с правами 0600.

На хосте/в shell работающего сервиса:

```bash
python scripts/backup.py \
  --database /var/data/agentpay.db \
  --output /var/data/backups/agentpay-20261024T020000Z.db
```

Имя должно быть новым. Это пример времени, а не автоматически выполняемое расписание. В локальном Docker:

```bash
docker exec agentpay python scripts/backup.py \
  --database /var/data/agentpay.db \
  --output /var/data/backups/agentpay-20261024T020000Z.db
docker cp agentpay:/var/data/backups/agentpay-20261024T020000Z.db ./agentpay-backup.db
```

Копия на том же диске не защищает от потери этого диска. Перенести ее в отдельно разрешенное зашифрованное хранилище с ограниченным доступом; проверить владельца, контрольную сумму и возможность чтения/восстановления. Реальные копии содержат персональные данные, хеши паролей и сессии — не прикладывать их к issues и CI artifacts.

Автоматического backup scheduler/upload в приложении нет. Назначить ответственного и расписание средствами хостинга, способными читать именно рабочий том. Предлагаемые, еще не подтвержденные цели пилота: RPO ≤24 часа, RTO ≤2 часа; суточные копии за 7 дней и недельные за 4 недели, если это соответствует договорным срокам. Регулярно выполнять восстановление в изолированный каталог. Не полагаться на сырые snapshots диска как на проверенный SQLite backup.

## 6. Восстановление и откат

Восстановление выполняется **только после остановки всех процессов приложения, использующих файл**. Флаг `--app-stopped` — подтверждение оператора, скрипт не может доказать остановку удаленного процесса. Не запускать восстановление из shell активного Render instance с продолжающим работу uvicorn. Использовать offline/maintenance процедуру хостинга с тем же томом либо согласованно перенести базу на остановленный хост в РФ.

Для отдельного чистого файла:

```bash
python scripts/restore.py \
  --backup /secure-backups/agentpay-selected.db \
  --database /var/data/restored-agentpay.db \
  --app-stopped
```

Для намеренной замены существующей базы:

```bash
python scripts/restore.py \
  --backup /secure-backups/agentpay-selected.db \
  --database /var/data/agentpay.db \
  --app-stopped --replace-existing
```

Без `--replace-existing` существующий файл не заменяется. С этим флагом сначала создается проверенная копия текущей базы `agentpay.db.pre-restore-<UTC>-<id>.db`, затем проверенная восстановленная база атомарно заменяет файл. Поврежденный backup, чужая/неподдерживаемая схема (сейчас поддержана версия 1), нарушение внешних ключей или занятый WAL-checkpoint блокируют замену. Не удалять неизвестные `-wal`/`-shm` вручную; если найден sidecar без основной базы, скрипт откажется и потребует разбор.

После запуска одной реплики проверить health, вход, число/суммы счетов, последний известный платеж и журнал. Восстановление старой БД возвращает старое состояние писем/сессий. Внешняя SMTP-отправка не отменяется откатом: перед повторными письмами сверить журналы провайдера, завершить прежние сессии по утвержденной процедуре и не пересылать уже ушедшую корреспонденцию. У автоматического rollback кода нет механизма отката внешних эффектов.

## 7. Почта, сбои и мониторинг

Включать SMTP после проверки отправителя, SPF/DKIM/DMARC у выбранного провайдера и реальной тестовой доставки на принадлежащий владельцу адрес. В текущем выпуске каждую отправку инициирует человек после согласования. Текст после редактирования требует нового согласования; измененный остаток требует нового письма. Не обещать автонапоминания, доставку в inbox или отслеживание прочтения.

Для исправления контакта карточка использует `PATCH /api/invoices/{id}/contact` с `email` и `notes`. Правка снимает согласования неотправленных писем. Если email изменился, старое письмо сохраняет прежнего адресата и больше не согласуется/отправляется: подготовить новый черновик. Примечания и контакт можно уточнить у оплаченного счета; отправка по нулевому остатку по-прежнему запрещена.

Если SMTP оборвал соединение после приема письма, UI может показать неподтвержденную отправку, хотя сервер уже принял сообщение. Автоматического повтора нет. Сначала проверить Message-ID/лог провайдера и исходящую почту, затем решать о повторном согласовании. Не создавать второй черновик лишь для обхода интервала.

Проверять доступность `/api/health`, 5xx/429, свободное место и рост WAL, возраст последней копии, ошибки SMTP, время ответа и обновления зависимостей. Health проверяет доступ к БД, но не подтверждает правильность всех остатков, доставку почты или наличие внешней резервной копии. Не писать тела CSV, пароли, cookie, SMTP-секреты и полную переписку в централизованный лог. Оператор должен иметь процедуру инцидентов, отзыва секретов, ограниченного доступа поддержки и обработки запросов на данные/удаление; автоматизированного self-service удаления аккаунта пока нет.
