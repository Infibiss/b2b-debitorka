# Процесс взыскания

Код: `server/recovery_rules.py` (правила), `server/recovery.py` (API), `server/recovery_templates.py` (документы), `server/financing.py` (финансирование). Тесты: `tests/test_recovery.py`.

## Этапы

| Этап | Статусы |
| --- | --- |
| Досудебная работа | Новый → Напоминания → Претензия готова → Претензия отправлена → Можно передавать в суд. Отдельно: обещание, нарушенное обещание, спор |
| Суд | Выбор маршрута → Ожидает пошлины → Пошлина оплачена → Проверка юристом → Готово к подаче → Подано → Приказ или решение |
| Исполнение | Исполнительный документ → банк или ФССП → деньги. Если денег нет: намерение о банкротстве или списание |

Два перехода происходят без действий пользователя. Долг с нулевым остатком становится оплаченным, а по истечении срока ответа на претензию открывается суд.

## Что считает код

- Маршрут: приказ для бесспорного документального долга до 750 000 ₽, иначе иск.
- Госпошлина по ст. 333.21 НК РФ, проценты по ст. 395 ГК РФ.
- Готовность к суду: договор, документы об исполнении, доверенность, подтверждение отправки претензии.
- Сроки: исковая давность, ответ на претензию, возражения на приказ, предъявление листа.
- Порог банкротства: 2 000 000 ₽ для компании, 500 000 ₽ для ИП, нужен судебный акт в силе.

Передачу в суд, проверку юриста и банкротство подтверждает руководитель. Автоматизация никогда не отправляет дело в суд сама.

## Документы

Претензия и судебные заявления используют один текст фактов. Шаблоны редактируются в кабинете. Каждый документ проверяет человек; подписание и подача выполняются вне системы, результат вносится в карточку.

## Финансирование

Система оценивает должника по четырём продуктам из `server/financing_catalog.json`. Заявка уходит партнёру только с согласия клиента. Сейчас заявками управляет оператор:

```bash
python -m scripts.financing_requests list
```

Погашение партнёру считается по банковским поступлениям от должника после даты финансирования.

## Должник и независимые дела

Карточка должника объединяет обзор, но не юридические состояния разных договоров. Каждому явно указанному договору соответствует `contract:<id>`; до указания договора каждый счёт ведётся отдельно как `invoice:<id>`. Счета объединяются только по явному выбору пользователя через `/api/workflow/contracts`. Название договора в текстовом поле не заменяет эту связь.

`GET /api/recovery/debtors/<id>` возвращает `cases`, `selected_case_id` и `read_only`. При нескольких делах общий обзор не принимает изменений состояния. Для работы с одним делом передаётся `?case_id=...` в GET/PATCH, actions, documents и register. Чужое либо отсутствующее дело даёт 404, неоднозначное изменение общей карточки — 409. Переписка и первичные документы выбранного дела ограничены его счетами; финансовый реестр остаётся источником остатков.

Обещание приостанавливает напоминания по делу до даты включительно по Москве. Начиная со следующего дня возможна следующая отправка, если нет паузы, спора, закрытия, истечения мандата и других ограничений. Сохраняются расписание и общий для контрагента/адресата интервал контактов. Частичное обещание тоже удерживает переписку по делу, но не изменяет остаток и не создаёт оплату. Запрет проверяется при подготовке задания и непосредственно перед отправкой уже подготовленного письма. Неоднозначная отправка не повторяется автоматически.

Прекращение взыскания, списание и соглашение останавливают напоминания выбранного дела, сохраняя финансовые записи. Автоархивирование оплаченного дела не архивирует соседние договоры. Общая ручная пауза/архив из списка должников относится ко всему контрагенту.

Если прежняя общая карточка уже содержала действия, при появлении нескольких дел требуется явное решение руководителя, к какому делу относится прежняя история: `POST .../legacy-assignment?case_id=...`. Оригинальные записи сохраняются, а полномочия отправки после переноса приостанавливаются до повторного запуска. История не копируется молча во все договоры.
