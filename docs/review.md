# AgentPay: независимая проверка спецификации и безопасности

Дата: 24.10.2026. Проверка выполнена отдельным агентом, который не реализовывал сервер и интерфейс. Основание — `docs/superpowers/specs/2026-10-24-agentpay-design.md` и `docs/superpowers/plans/2026-10-24-agentpay-mvp.md`.

## Область

Прочитаны серверные модели, схема SQLite, импорт CSV, аутентификация и CSRF, tenant-фильтры всех финансовых ресурсов, жизненный цикл писем, SMTP, адаптер Yandex, формы и карточка счёта. Написаны отдельные регрессионные проверки `e2e/test_security_review.py` и браузерные сценарии `e2e/agentpay.spec.ts`.

Это проверка исходного кода и локальных сценариев. Она не является внешним пентестом или проверкой инфраструктуры действующего хостинга. Внешние SMTP и Yandex API при независимых проверках не вызывались.

## Найденные проблемы и состояние

### P1 — общий SMTP был доступен любому публично зарегистрированному аккаунту: исправлено и перепроверено

До исправления `SMTP_HOST` и `SMTP_FROM` включали почту для всех tenants. Независимое воспроизведение: новый аккаунт получил `smtp_configured=true`, создал счёт с произвольным получателем, изменил текст, согласовал и получил HTTP 200 при отправке через SMTP оператора. Использовалась локальная подмена SMTP-класса; письмо во внешнюю сеть не отправлялось.

После исправления SMTP требует точного совпадения `SMTP_TENANT_ID` с tenant аккаунта. Без привязки и для второго аккаунта настройки показывают `false`, отправка возвращает 409. Авторизованный tenant может выполнить отправку один раз; повторный вызов запрещён. Два регрессионных теста сначала упали на исходной реализации и прошли после исправления.

Для первого выпуска это привязка одного корпоративного ящика к одной компании. Она не означает поддержку самостоятельного подключения почты каждой компанией.

### P2 — обещание на сегодня отображалось как нарушенное: исправлено и перепроверено

В карточках «Внимание сегодня» использовалось сравнение `new Date(promise_date) < new Date()`. Дата без времени превращается в начало дня, поэтому обещание на сегодня ошибочно становилось нарушенным в течение этого же дня. Сервер сравнивал календарные даты корректно. Интерфейс переведён на сравнение календарных дат; браузерная регрессия с сегодняшним обещанием прошла на desktop и mobile.

### P2 — модальная карточка счёта не удерживала клавиатурный фокус: исправлено и перепроверено

У карточки есть `aria-modal=true`, однако исходный код блокировал только прокрутку и Escape. Фокус мог оставаться в фоновом реестре. Добавлены перенос, удержание и восстановление фокуса. В браузерном сценарии перенос внутрь и удержание при Shift+Tab подтверждены на desktop и mobile. Вложенная форма использует отдельный Dialog с восстановлением фокуса.

### P2 — расходы общего LLM-ключа при открытой регистрации: ограничены

Вместо передачи клиентских данных модель получает только один из двух вариантов тона. Добавлен общий кэш нейтральных фраз: успешный ответ — на пять минут, fallback после ошибки — на 30 секунд, конкурентные промахи сериализуются. При постоянных настройках это ограничивает частоту успешных генераций двумя вызовами на пять минут на процесс; при ошибках возможны более частые попытки. В кэше нет реестров и переписки клиентов. Это ограничение расходов для одного процесса, а не учёт потребления по каждому платному аккаунту.

## Независимые проверки API

Команда: `python3 -m pytest -q e2e/test_security_review.py`.

Финальная команда: `.venv/bin/python -m pytest -q e2e/test_security_review.py`.

Результат после исправления SMTP и добавления редактирования контакта: **6 passed (1.31s)** на FastAPI 0.162.0, Starlette 1.9.0, pytest 9.1.1. Одно предупреждение Starlette касается будущей замены транспорта `httpx` в TestClient; сценарии прошли без ошибок. Ранний прогон на старом глобальном окружении в финальную оценку зависимостей не включается.

Проверено:

- Новый аккаунт начинает с пустым реестром и не наследует SMTP оператора.
- Второй tenant не читает и не изменяет чужой счёт, обещание, платёж, статус или письмо; не согласовывает и не отправляет его, не видит его в экспорте/обзоре.
- Отсутствующий/неверный CSRF и посторонний Origin не позволяют изменить данные.
- Частичный платёж снимает согласование; устаревший текст нельзя заново согласовать или отправить.
- Повторный платёж с тем же номером не меняет остаток повторно; переплата отклоняется; после полной оплаты новое письмо запрещено.
- SMTP-имитация для разрешённого tenant вызывается один раз; повторная отправка и попытка другого tenant блокируются.
- Исправление email снимает согласование; старый получатель не подменяется автоматически и старое письмо нельзя отправить. Новый черновик получает актуальный адрес. Массовое присваивание финансовых полей через contact endpoint запрещено.

Дополнительно по коду: деньги принимаются строгими целыми копейками; SQL-запросы ресурсов содержат tenant-фильтр; записи платежей и изменения остатков находятся в транзакции; пароли хешируются Argon2; сессии непрозрачные, серверные, cookie HttpOnly/SameSite. В production конфигурация требует HTTPS APP_URL и Secure cookie. CSV импорт сначала валидируется полностью; экспорт экранирует потенциальные формулы.

## Браузерная проверка

Проверка выполняется на production-сборке с отдельной временной SQLite, без подключения внешних SMTP/LLM. Проекты — Chromium desktop 1440×1000 и Pixel 7. Сценарии включают лендинг, этапы процесса, калькулятор, FAQ, регистрацию, создание счёта, согласование, отсутствие фиктивной отправки, обещание, две оплаты, reload, выход/вход, CSV-ошибки и повторы. Дополнительно проверена коррекция контакта: старое письмо возвращает 409 при согласовании, новое получает актуальный адрес, контакт сохраняется после reload. Проверяются отсутствие горизонтального переполнения и клавиатурный фокус карточки. Скриншоты сохраняются в `e2e/results/`.

Финальная команда: `PATH="$PWD/.venv/bin:$PATH" npm run test:e2e`.

## Ограничения проверки и эксплуатации

- Проверено локальное поведение приложения; реальная доставка SMTP, биллинг Yandex и внешний deployment требуют собственных доступов и проверки.
- Локальные ограничения запросов и кэш рассчитаны на один процесс; распределённая защита и квоты потребуют отдельного слоя при масштабировании.
- Принятие письма SMTP-сервером не доказывает доставку в папку получателя. После неоднозначного SMTP-сбоя автоматического повторения нет.
- Интеграция с 1С в первом выпуске — импорт CSV. Прямой коннектор, сверка с банком и распознавание входящей переписки не должны заявляться как реализованные.
- Реальный контур работы с данными и операционные настройки нужно оценивать на выбранном хостинге отдельно от успешных локальных тестов.
