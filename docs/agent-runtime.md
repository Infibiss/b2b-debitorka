# Агент входящих сообщений: запуск и ограничения

Проверено 24.10.2026. Реализован настоящий LangGraph `StateGraph`: ingest → Yandex structured extraction → проверка доказательств/финансов/мандата → proposal → `interrupt` для человека → повторная проверка → атомарное действие → outcome. Вход MVP — ручная вставка текста выбранного сообщения и явный выбор счёта. Почтового polling, автоматических звонков, свободного MCP, банковской или судебной отправки в этом модуле нет.

## Доступ оператора к платной модели

`YANDEX_API_KEY` берётся только из окружения процесса. `YANDEX_AGENT_MODEL` — необязательная замена `YANDEX_MODEL`; пустое значение использует существующую текстовую модель. Адрес API фиксирован, redirects и proxy environment отключены, таймаут 8 секунд, один запрос до 900 выходных токенов. В запрос передаётся введённый текст, время получения и инструкция; реестр счетов/контактов не передаётся.

На публичном production экземпляре **обязательно** задать `YANDEX_AGENT_TENANT_IDS` — список UUID организаций пилота через запятую. При пустом списке, чужой организации или любой невалидной записи платный вызов запрещён. Это распространяется и на прежнюю генерацию общих фраз писем: для остальных организаций остаются шаблоны. В development/test отсутствие привязки разрешено; если список задан, он соблюдается и локально.

Оператор входит в нужную организацию и читает `GET /api/agent/status`: ответ содержит её `organization_id`, `enabled`, `observability_configured` и причину. После проверки принадлежности этот UUID добавляется оператором в конфигурацию хостинга. Клиент не может сам включить свою организацию изменением API-параметра. Секрет ключа и содержимое `.env` endpoint не возвращает.

Дополнительные ограничения: не более 30 новых сообщений на организацию за час и 1000 глобально за сутки в бизнес-БД, до двух одновременных провайдерских запросов процесса. Повтор одного `idempotency_key` не создаёт новое событие; другой текст с тем же ключом даёт конфликт. Это ограничения числа запросов; они не являются рублёвым бюджетом. Установить лимит бюджета Yandex отдельно. Для оценки расходов можно задать проверенные оператором `YANDEX_AGENT_INPUT_RUB_PER_1K` и `YANDEX_AGENT_OUTPUT_RUB_PER_1K`; без них стоимость помечается как недоступная, а не нулевая.

## API и данные

- `POST /api/agent/ingest`: `{invoice_id, text, received_at?, idempotency_key}`. Время — ISO с часовым поясом; thread ID и tenant назначает сервер.
- `GET /api/agent/proposals`, `GET /api/agent/proposals/{id}`: источник, дословные цитаты с вычисленными сервером offsets, нормализованные факты, причины, финансовый снимок, статус и результат.
- `POST /api/agent/proposals/{id}/review`: `{decision: "approve"|"reject", reason?: string}`. Нужны обычная сессия/CSRF/Origin. Resume payload графа сам по себе прав не даёт.
- `POST /api/agent/proposals/{id}/revise`: `{text, idempotency_key}`. Создаёт отдельную редакцию, сохраняет старый текст и отменяет действие предыдущей редакции. Исполненные предложения не редактируются.

Только `review_required` допускает подтверждение. `handoff` означает отсутствие проверенных фактов, провайдерскую ошибку, отсутствие доступа или несоблюдение мандата. `stale` требует новой редакции; истечение 24 часов, изменение финансового снимка или политики контрагента блокирует действие. `executed`, `rejected`, `superseded` сохраняют историю.

Явное обещание фиксирует только извлечённую частичную сумму, если оператор включил `agent_promises_allowed` и срок укладывается в мандат. Спор фиксируется только после подтверждения. «Мы оплатили» создаёт `agent_verifications` со статусом `open`, **не** платёж и **не** уменьшение остатка. Поступление сверяется обычным финансовым процессом. Неполная дата, отрицание, старая цитата, несколько вариантов, отсутствующая валюта или неподтверждённая сумма требуют ручного разбора.

Исходный текст и evidence хранятся в tenant-scoped бизнес-БД. Checkpoint содержит ID/tenant/статус; он не является реестром денег. SQLite checkpoint — файл `<DATABASE_PATH>.agent-checkpoints.sqlite3` рядом с бизнес-БД, права 0600; включить его в локальный план резервного копирования через SQLite backup API либо согласованную остановку процесса, не копировать один файл при активном WAL. При `DATABASE_URL` используется настоящий PostgreSQL checkpointer в той же БД. Потерянный checkpoint можно восстановить из сохранённого proposal; запись финансового действия и terminal status атомарны. Повторное подтверждение не повторяет исполнение.

## Локальный Langfuse

Langfuse опционален: базовый VM-запуск использует приложение и его PostgreSQL. Без project keys агент работает без телеметрии. При ошибках инициализации/SDK, записи span или flush бизнес-действие продолжает обычную проверку и транзакцию; наблюдаемость не разрешает действие и не заменяет бизнес-аудит. `observability_configured` означает наличие сконфигурированного клиента, не проверку доставки — для неё нужен canary.

```sh
.venv/bin/python scripts/langfuse_local.py init
docker compose --env-file var/langfuse-local.env -f compose.langfuse.yml up -d
.venv/bin/python scripts/langfuse_local.py verify
.venv/bin/python scripts/langfuse_local.py run-app
```

`init` создаёт только отдельный `var/langfuse-local.env` с правами 0600, сохраняет существующие credentials и ничего секретного не печатает. Файл игнорируется Git. `run-app` передаёт Langfuse credentials в окружении и вызывает обычный `scripts.run_local`, который загружает пользовательский `.env` без перезаписи переменных окружения. Не запускать второй процесс на уже занятом порту; root launcher/оператор сначала останавливает прежний экземпляр после резервной копии.

UI доступен только на `http://127.0.0.1:3033`. Локальный пользователь — `operator@agentpay.invalid`; сгенерированный пароль `LF_USER_PASSWORD` находится только в приватном bootstrap-файле. Не публиковать этот файл или контейнерные environment. Для остановки с сохранением данных: `docker compose --env-file var/langfuse-local.env -f compose.langfuse.yml stop`. `down -v` удаляет историю и требует осознанного решения оператора.

Контур — шесть контейнеров: web, worker, PostgreSQL, ClickHouse, Redis, SeaweedFS. Docker на машине проверки имел 8 ГБ памяти; суммы лимитов контейнеров около 5,4 ГБ, фактическое потребление ниже и зависит от нагрузки. Первоначальный лимит ClickHouse 1 ГБ вызвал реальные ошибки OvercommitTracker даже на нескольких синтетических traces; он увеличен до 2 ГБ. Это отдельная локальная система: 4 ГБ для приложения и всего контура нельзя считать проверенной безопасной конфигурацией. Официальное руководство Langfuse Compose рекомендует VM от 4 cores / 16 GiB; 8 ГБ можно оценивать как ограниченный эксперимент с нагрузочными проверками, а не заявленный production minimum. [Официальное размещение Compose](https://langfuse.com/self-hosting/deployment/docker-compose).

Образы закреплены по проверенным дайджестам. SeaweedFS выбран как официально поддерживаемое Langfuse S3-хранилище; анонимные MinIO registries в этой среде оказались недоступны. [Langfuse blob storage](https://langfuse.com/self-hosting/deployment/infrastructure/blobstorage).

Инструментирование использует настоящий Python SDK Langfuse 5.0.4/OpenTelemetry: извлечение и граф, модель/версия prompt, статус, токены, задержка и рассчитанная по заданным тарифам стоимость. Полный текст, цитаты, контакты и финансовый снимок в spans не передаются. Автоматические LangChain callbacks не подключены, автоматический LangSmith tracing для графа выключен. Бизнес-ошибка передаётся наружу после выхода из SDK context, чтобы SDK не записал её текст в exception event.

`verify` отправляет минимальную синтетическую generation, делает flush и читает её через актуальный `GET /api/public/v2/observations` с ограниченным временным интервалом; проверяет I/O и пишет только безопасный delivery report в `var/langfuse-canary.json`. Старые `/api/public/traces` в новом Langfuse v4 недоступны и не служат доказательством доставки. [Совместимость API](https://langfuse.com/docs/compatibility).

Подключение удалённого Langfuse требует отдельно разрешённых host/project keys и проверки размещения/сроков хранения. Локальный контур с синтетикой не разрешает автоматически выгрузку клиентских сообщений в облако. Политика хранения бизнес-текста/checkpoint/backups и договоры обработки остаются ответственностью оператора.

## Проверки и оценки

```sh
.venv/bin/python -m pytest tests/test_agent_*.py -q
.venv/bin/python -m server.agent_evals --mode replay --out var/agent-eval-replay.json
# Платные обращения только на приложенной синтетике, если ключ уже в окружении:
.venv/bin/python -m server.agent_evals --mode yandex --out var/agent-eval-yandex.json
```

В `docs/evals` сохранены агрегаты реального Yandex-прогона, отдельного replay защитных проверок, полный synthetic application→Langfuse canary и снимок ресурсов, без переписки и ключей. Это малый синтетический набор, не измерение производственного качества или влияния на собираемость. Входящий mail connector, размеченная выборка клиента, автоматические retention jobs и внешние звонки требуют дальнейшей отдельной реализации и проверки.
