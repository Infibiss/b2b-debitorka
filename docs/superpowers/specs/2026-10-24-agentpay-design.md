# AgentPay — продукт и границы первого выпуска

Дата: 24 октября 2026. Заказчик разрешил самостоятельно исследовать, составить план и реализовать максимум без промежуточных согласований. Исходный отчёт: AgentPay_B2B-debitorka_prorabotka.pdf, 25 страниц, изучен полностью. В репозитории исходного кода нет.

## Решение
Коммерческий первый выпуск для дистрибьюторов и производителей: контроль ранней B2B-просрочки, подготовка переписки, человеческое согласование, обещания оплаты и регистрация фактических поступлений. Судебное представительство, автоматическое списание денег, универсальный прямой коннектор 1С и обучение скоринга требуют данных, договоров и внешних доступов; не маскируются кнопками с фиктивным результатом.

Рассмотрены три подхода: универсальная автономная юридическая платформа (непроверяемая ответственность и интеграции), только маркетинговый сайт (не решает задачу), узкий рабочий продукт с оператором и контролем действий (выбран). Этот выпуск можно продавать как инструмент кредит-контроля и основу сопровождаемого пилота, не как полностью автономное взыскание.

## Продукт
1. Публичный сайт: выразительная редакционная композиция, спокойный фон, тёмный зелёный, лаймовый акцент, большие заголовки, сюжет от поставки до поступления. Четыре интерактивных этапа, калькулятор стоимости замороженных денег, прозрачные тарифы, FAQ, регистрация. Никаких выдуманных клиентов, отзывов и процентов результата. Представленный процесс не называется «демо».
2. Кабинет: обзор портфеля, aging, реестр с поиском и фильтрами, карточка долга, импорт CSV с проверкой, создание счёта, мягкое/деловое письмо, редактирование и согласование, отправка только при настроенном SMTP, обещание, спор/пауза, частичные оплаты, экспорт CSV, журнал действий, настройки компании и правила контакта.
3. Пустой аккаунт начинает с пустого реестра; нет автоматической подстановки чужих или вымышленных долгов.

## Архитектура
React + TypeScript + Vite, lucide-react, CSS и небольшие motion-переходы; API FastAPI/Pydantic; SQLite WAL, целые копейки, tenant_id на каждом ресурсе, транзакции. Один экземпляр сервиса с постоянным диском для первых пилотов. Секреты SMTP/LLM в окружении. Пароли Argon2, непрозрачные серверные сессии, HttpOnly/SameSite cookie, CSRF, origin-проверка и лимиты запросов. Сервер обслуживает production-сборку фронтенда. Docker и Render Blueprint; тот же контейнер переносим в российское облако.

## ИИ и данные
Правила приоритета объяснимы (дни, сумма, нарушенное обещание, спор/пауза). Не выдаём балл за вероятность оплаты. Базовые письма строятся из подтверждённых реквизитов; опциональный Yandex AI Studio перефразирует только текст, а финансовые факты подставляет код. Все внешние отправки требуют согласования; изменение содержания снимает согласование. Платежи немедленно меняют остаток и запрещают новое письмо по закрытому долгу. При недоступном LLM — безопасный шаблон.

## Проверка и выпуск
pytest: точность денег, CSV с локалями и повторами, tenant isolation, CSRF, аутентификация, повторные оплаты, закрытый долг, согласование/отправка. TypeScript и production build. Playwright: главная на desktop/mobile, регистрация → импорт → долг → письмо → обещание → частичная/полная оплата, сохранение после reload, выход и вход. Визуальная проверка в браузере. CI проверяет Python, TS, build, e2e, контейнер; основной CD запускает Render нативно после успешных CI checks (`checksPass`). Hook остается отдельной альтернативой при отключенном нативном auto-deploy.

## Критерии приёмки
Работают все перечисленные переходы, данные сохраняются на сервере, разные компании не читают данные друг друга, нет фиктивного «отправлено», все суммы считаются в копейках, основной сценарий доступен с телефона, reduced-motion поддержан, секретов в репозитории нет. Непроверенные внешние интеграции и юридические вопросы перечислены в документации и в итоговом сообщении.
