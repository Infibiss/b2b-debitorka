# CD Mandato через GitHub: предлагаемый вариант

Репозиторий Infibiss/b2b-debitorka на 08.11.2026 публичный. На production VM не устанавливается универсальный GitHub Actions runner: он способен исполнять задания из недоверенного workflow/PR. CI остаётся на GitHub-hosted runners.

## Рекомендуемый вариант: сервер забирает проверенный релиз

На существующей VM systemd timer каждые пять минут проверяет main и успешный Verify именно для полного текущего SHA. Используется публичный GitHub API, без сохранения GitHub токенов/SSH-секретов. Ожидаемая частота — 24 API-запроса/час в спокойном состоянии, с резервом до публичного лимита; при 403/429/CD API errors — отказ от обновления и backoff.

Проверки: идентичность репозитория, путь ci.yml, event=push, branch=main, conclusion=success, полный SHA и текущий head main. Проверка устаревания повторяется до переключения версии. Непроверенный main, PR, чужой репозиторий или неоднозначный ответ не разворачивается.

Код загружается по точному SHA в изолированный локальный git cache. Транспортный shell deployment отделяется от общего локального release script, с сохранением проверок SHA/безопасности архива, блокировки одного deploy, сборки до остановки сервиса, обязательной резервной копии и проверки trusted HTTPS. Запущенный current SHA не обновляется повторно. История результата хранится в журнале systemd.

Не включать существующий GitHub-hosted SSH workflow без сетевой схемы. Не открывать TCP22 для 0.0.0.0/0 и не выдавать GitHub права менять облачный firewall. SSH остаётся только с явно разрешённых IP оператора.

Бюджет: существующая VM/диск, без новых облачных сервисов. Интервал добавляет до пяти минут к времени CI. Развёртывание после неуспешного обновления не повторяется бесконечно на том же SHA; автоматического destructive restore нет. Любой код production-ветки, даже прошедший CI, получает возможности текущего приложения/сборки: доступ на запись в main должен быть ограничен владельцем.

## Альтернативы

1. Немедленный push-deploy из GitHub-hosted runner: требует отдельного закрытого канала либо ограниченного управления временным сетевым допуском. Дополнительные доступы/обслуживание; на первом запуске не предлагается.
2. Универсальный self-hosted runner прямо на production VM: не рекомендуется для текущего публичного репозитория из-за исполнения workflow рядом с production.

## Приёмка после согласования

Тесты разрешения только точного успешного main SHA, запрета PR/ошибки/устаревшего SHA/повторного deploy; сохранение ручного SSH deploy; shell syntax; полный CI. На сервере сначала dry-run, затем один контролируемый deploy текущего проверенного SHA, проверка HTTPS, неизменности финансовых записей и восстановления backup. Только затем включить timer.
