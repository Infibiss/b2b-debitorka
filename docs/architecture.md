# Архитектура и решения первого выпуска

## Почему этот продукт

Исходный отчёт предлагает сервис с оператором и юристом, а не только софт. Исследование не подтвердило пустую нишу: международные платформы уже предлагают AI-переписку, очереди, обещания и сопоставление оплат; в русскоязычном сегменте есть решения 1С и специализированные продукты. Поэтому первая проверяемая продажа — сопровождаемый кредит-контроль для поставщика. Договор, коммерческая цена и фактическая собираемость проверяются отдельно от качества кода.

Реализован путь: аккаунт компании → импорт/создание счёта → остаток/приоритет → письмо → редактирование/согласование → отправка при подключённой корпоративной почте → обещание → частичная/полная оплата → прекращение напоминаний. Нет автоматически добавленных клиентских долгов. Публичная анимация — иллюстрация самого процесса, не выдуманный кейс клиента.

## Выбор стека

| Решение | Почему выбрано | Граница |
|---|---|---|
| React + TypeScript + Vite | Самостоятельный responsive-клиент, строгие DTO, компактная production-сборка; отделён от Python API | Marketing HTML сейчас клиентский: поисковая индексация и social previews используют метаданные, серверного рендера контента нет |
| FastAPI + Pydantic | Явные API-контракты, удобные интеграционные тесты, близость к будущей аналитике/ML | Один экземпляр; нет распределённых задач |
| SQLite WAL | Транзакции, строгая связь платежа и остатка, простая эксплуатация первых пилотов | Постоянный локальный диск, один writer; несколько реплик требуют PostgreSQL и общей очереди |
| Целые копейки | Денежные операции не зависят от ошибок float | Процентный калькулятор — оценка стоимости финансирования, не бухгалтерское начисление |
| Argon2 + серверные сессии | Непрозрачные случайные токены, отзыв при выходе, минимум клиентских секретов | Нет MFA, самостоятельного reset-password, ролей/приглашений |
| SMTP, привязанный к tenant | Реальная отправка через согласованный ящик; другие публичные аккаунты не наследуют его доступ | В одном экземпляре поддержан один отправляющий tenant; multi-tenant secret vault позже |
| Yandex AI Studio опционально | Модель получает только общий запрос на формулировку и тон, без клиентских/финансовых сведений | Ключ нужен только для AI-варианта; шаблонный режим всегда доступен |
| GitHub Actions + Docker + Render Blueprint | Один переносимый non-root образ, воспроизводимые зависимости, нативный Render deploy после CI (`checksPass`) | Нужны подключенный Git-провайдер и постоянный диск; успешный CI не заменяет проверку статуса deploy и health |

C++/Rust/Go не дают сейчас проверенного преимущества: основная работа — транзакции, валидация, интерфейс и ожидание внешней почты/LLM. Нет измеренного CPU bottleneck, оправдывающего более дорогую реализацию. Если он появится, сначала профилирование и нагрузочный тест, затем локальная оптимизация. GPU не нужен для текущего продукта и табличного baseline.

Render использует `RENDER_EXTERNAL_URL` как стандартный HTTPS origin, если `APP_URL` не задан; собственный домен задается через `APP_URL` с приоритетом над Render URL. Основной CD — **After CI Checks Pass**. Сохраненный hook-job включается только отдельным `RENDER_DEPLOY_MODE=hook` после отключения нативного auto-deploy, чтобы не создавать дубли. Подробности — в `docs/operations.md`.

## Границы модулей

- `server/database.py`: схема и транзакции, WAL, внешние ключи, миграционная версия.
- `server/models.py`: строгие входные контракты и проверка данных.
- `server/business_time.py`: календарные даты Europe/Moscow, независимо от timezone хоста.
- `server/csv_import.py`: CSV, локализованные даты и Decimal → копейки.
- `server/llm.py`: ограниченная генерация общих фраз, валидация, кэш, fallback.
- `server/main.py`: HTTP, сессии/CSRF/Origin/лимиты, доменные операции, SMTP и static serving.
- `web/src/api.ts`: общие DTO и запросы с CSRF.
- `web/src/components/Landing.tsx`: сайт и интерактивный сценарий.
- `web/src/components/Workspace.tsx`: обзор/реестр/переписка/настройки.
- `web/src/components/DebtDrawer.tsx`: счёт, письма, обещания, поступления и история.
- `web/src/components/InvoiceForms.tsx`: создание и preview/commit импорта.
- `scripts/backup.py`, `restore.py`: согласованный snapshot и проверяемое offline-восстановление.

## Правила, защищающие деньги и отношения

1. Каждая выборка/изменение финансового ресурса ограничено tenant. Идентификатор сам по себе не даёт доступа.
2. Принятие платежа, увеличение оплаченной суммы, снятие согласования писем и запись события — одна транзакция.
3. Повторный номер платежа по тому же счёту с теми же данными идемпотентен; с другими данными — конфликт. Переплата отклоняется.
4. Нельзя отправить письмо без согласования, по закрытому/спорному/приостановленному счёту, с устаревшим остатком или получателем.
5. Редактирование содержания и контакта снимает согласование. После изменения остатка/адреса нужен свежий черновик.
6. SMTP-сбой не превращается в успех. При неоднозначном сбое нет автоматического повтора: оператор сверяет почтовый журнал.
7. Деньги покупателя поступают прямо поставщику; приложение не выполняет платёжные операции.
8. Балл приоритета — объяснимое правило, не вероятность оплаты. DSO не вычисляется из неполного реестра просрочек.

## Следующий объём после первых оплаченных пилотов

В порядке подтверждённой потребности: безопасные исправления финансовых первичных данных/сторнирование, batch-импорт подтверждённых оплат с preview, прямой коннектор конкретной конфигурации 1С, команды и роли, reset-password/проверка email, tenant-specific SMTP vault, PostgreSQL/очередь/outbox, разбор входящей переписки. Юридические документы и представительство — отдельный продуктовый и правовой контур.

ML допускается только после появления point-in-time истории: договорный срок, состояние счёта на дату решения, фактические allocation/payment timestamps, действия/ответы и цензурирование незакрытых наблюдений. Сначала temporal backtest правил, затем CatBoost/survival и измерение экономического эффекта в контролируемом пилоте. Подробности и источники — `docs/research/ml-data.md`.
