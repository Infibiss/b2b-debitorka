# Аудит рабочих сценариев AgentPay

Дата: 24 октября 2026. Проверка HTTP API, настоящего временного SQLite и конкурентных запросов. SMTP заменён контролируемой границей протокола: внешних писем, банковских операций и обращений к реальным клиентам не было. Рабочая БД, `.env` и ключи не читались и не изменялись.

## Воспроизведённые и исправленные ошибки

| Приоритет | Сценарий | Было | Стало |
| --- | --- | --- | --- |
| P1 | Согласовать письмо → исправить банковские реквизиты → отправить старое письмо | Отправлялись старые реквизиты | Старые неотправленные письма навсегда теряют возможность согласования/отправки; нужен новый черновик |
| P2 | После согласования изменить компанию, имя отправителя или Reply-To | Подпись могла устареть, а заголовки менялись без нового просмотра | Любое фактическое изменение этих настроек инвалидирует старые неотправленные письма; редактирование текста не обходит запрет |
| P2 | SMTP подтвердил DATA, затем завершение QUIT завершилось ошибкой | Письмо становилось `failed`, хотя уже было принято; ручной повтор мог задвоить доставку | Подтверждённое письмо становится `sent` ровно один раз; повторные approve/send запрещены |
| P1 | Учётный CSV содержит сумму счёта, оплаты и остатки, в том числе заголовки «Оплачено, руб.», «Остаток (руб.)», `Paid Amount` | Неподдерживаемые столбцы молча отбрасывались, что могло завысить импортируемый долг | Любой неизвестный или неподдерживаемый финансовый столбец останавливает весь импорт; перенос начальных оплат и mapping не имитируются |
| P2 | Два запуска одновременно создают новую БД | Оба могли прочитать schema version 0; второй повторно выставлял v1 поверх v2 и падал на уже существующей колонке. Отдельно воспроизведён `database is locked` при одновременном включении WAL | Чтение версии и вся цепочка 0→1→2 выполняются под одним `BEGIN IMMEDIATE`; WAL включается после commit с ограниченным повтором только временной блокировки |

Проверки сначала падали: пять сценариев подтвердили дефекты отправки, ещё три — обход первичной проверки финансовых заголовков; отдельные RED воспроизвели гонку bootstrap и временную блокировку WAL. После исправлений независимый набор `tests/test_real_world_audit.py` содержит 29 проходящих проверок. Таймаут до положительного подтверждения DATA по-прежнему даёт `502`/`failed`, требует ручной сверки и не вызывает автоматический повтор.

## Сохранность данных и миграция

Схема v2 добавляет явное `messages.invalidation_reason`. Суммы, финансовые снимки и источник текста не используются как технические маркеры. Изменение ставки, интервала между письмами и сохранение идентичных настроек не инвалидируют согласования. История уже отправленных писем сохраняется.

На копиях временных БД проверены повторный запуск миграции v1→v2, сохранение остатков и отправленной истории, восстановление резервных копий v1/v2. Старые неотправленные письма v1 требуют нового черновика: происхождение их реквизитов невозможно подтвердить. Восстановленная v1 мигрирует только при следующем запуске приложения. Рабочую БД этим аудитом не мигрировали.

Для bootstrap сначала принудительно воспроизведено уязвимое расписание двух чтений version 0: до исправления получен `duplicate column name: invalidation_reason`, после исправления тест проходит. Затем 20 пар реальных параллельных запусков на полностью новых временных файлах прошли без mock. Регрессия также включает 10 пар свежих стартов, проверку конечных v2/WAL и повтор после временного `SQLITE_BUSY`. Это не меняет эксплуатационное ограничение одного worker/экземпляра сервиса.

## Подтверждённые сценарии

- Один банковский номер можно распределить между несколькими счетами; повтор той же записи одного счёта не удваивает поступление. Общие остатки и aging сходятся.
- Два одновременных идентичных полных платежа создают одну запись и одно событие. Повтор после закрытия идемпотентен.
- Переплата, отрицательная/нулевая сумма, boolean и дробные копейки отклоняются без изменения реестра.
- Изменение текста старого черновика после частичной оплаты не обходит проверку остатка. Отправленное письмо нельзя перезаписать из старой вкладки.
- Обещание, пауза и спор не позволяют заново открыть оплаченный долг. Будущая дата обещания сохраняется при временной паузе; после оплаты обещанная сумма равна нулю.
- Одновременный импорт одного CSV создаёт один счёт. Unicode-пробелы в суммах, кириллица, кавычки, разделитель внутри примечания и многострочное примечание сохраняются правильно. Невалидная точность или неподдерживаемый адрес в смешанном CSV отменяют весь импорт.
- В импорте разрешены только документированные столбцы. Неизвестные заголовки, включая произвольные дополнительные столбцы, отклоняются; оператор должен подготовить файл по шаблону. Это строгий безопасный контракт, а не автоматическое распознавание бухгалтерской выгрузки.

## Функциональные пробелы, а не нарушения текущего API

| Важность для эксплуатации | Ограничение |
| --- | --- |
| P1 для достоверного реестра юрлиц | Дубликат определяется точной парой `company + number`, как предусмотрено текущим контрактом. Другое написание того же юрлица с тем же ИНН может создать второй долг; разные юрлица с одинаковыми названием и номером могут быть отклонены как дубликат. Нужны отдельная идентичность контрагента, нормализация и миграция; перестройка схемы счетов в этот фикс не включена. |
| Блокер полноценного банковского учёта | Нет операций возврата, сторнирования и исправления ошибочного платежа. Отрицательные записи безопасно запрещены; этот запрет не заменяет корректирующий финансовый процесс. |
| Ограничение ручного распределения | Идемпотентность действует на запись платежа одного счёта. Без источника банковской выписки сервис не может доказать, что один банковский платёж не распределён сверх его общей суммы по разным счетам. |
| P2, требует продуктового решения | Интервал отправки действует на один счёт. По двум счетам одного клиента сейчас возможны два письма подряд; общего ограничения по контрагенту/почтовому адресу нет. |
| P2, отдельный сценарий | Можно перенести дату обещания, но отдельной отмены обещания пока нет. Возврат из паузы восстанавливает сохранённое обещание. |

Ограничения идентичности и области cooldown закреплены тестами текущего поведения, без искусственного красного требования к ещё не принятому контракту. Поддержка начальных оплаченных сумм и банковской сверки при импорте также не подразумевается этим аудитом; правила импорта финансовых колонок описаны отдельно в `docs/data-contract.md`.

## Команды

```sh
TZ=UTC .venv/bin/python -m pytest tests/test_real_world_audit.py -q
TZ=UTC .venv/bin/python -m pytest -q
```

Фокусированный результат: **29 passed**. Полный запуск после всех параллельных исправлений: **127 passed**, одна неблокирующая deprecation-подсказка тестового клиента Starlette, 9,64 с. Внешняя отправка, банковская сверка и эксплуатационная нагрузка этим результатом не подтверждаются.
